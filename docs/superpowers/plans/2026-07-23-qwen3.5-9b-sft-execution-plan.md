## 1. 目标与冻结边界

本轮验证 52 条高质量示范能否改善 Qwen3.5-9B 在现有 v4 Agent 中的图像理解、调查方向、工具使用、Evidence 绑定和二元裁决。模型继续学习现有阶段 schema，训练框架固定为 ms-swift + DeepSpeed，不自写训练循环。

冻结约束：

- 唯一训练候选来源：`ifv-scoring-gold-v1-reviewed-52-20260723`。
- `ifv-scoring-gold-v1-legacy-20-simple-20260723` 只做独立回归，禁止进入教师生成、SFT、调参和 checkpoint 选择。
- 52 条中 38 条 refuted、14 条 supported；保持自然分布，不按标签重采样或加权。
- Agent 和 Gemini 教师只读取 `runtime_input/cases.jsonl`、原图和真实工具结果。
- `evaluator_private/gold.jsonl` 只在一组 rollout 全部结束后离线读取，绝不进入 Agent、教师 Prompt、工具结果或 SFT 样本。
- 隐藏 reasoning 只作诊断 artifact，不进入后续上下文，也不作为 SFT loss target。
- 不要求轨迹命中 gold 的原 URL；允许其他真实来源，但必须证明同一 subject、event、slot 和 relation。
- Prompt 保持现有简洁版本。本轮不为教师失败增加 case 规则。

## 4. 先冻结 case split

在调用 Gemini 前生成版本化 `case_split.jsonl`：

- 44 条 train，8 条 validation；不设置内部 test，旧 20 承担最终独立评测。

- 同图哈希、同 source family、同 subject-event 或明显近重复 case 必须在同一 split。

- split 一旦教师生成开始即冻结；不能为改善结果移动失败 case。

若 validation case 的教师轨迹三次均不合格，可在训练前生成一次新的 split revision，用同标签、同去重约束的 train case 替换，并重新冻结；旧 revision 完整保留。

## 5. Gemini 教师轨迹生成

### 5.1 运行方式

- 显式使用 `teacher-gemini`、稳定版 `gemini-3.6-flash`、Gemini Interactions 和当前 v4 runtime。
- 输入与真实 Agent 一致：image-only public row，没有 claim、label、key error 或认证证据。
- 初始每 case 一条完整轨迹，先跑 2 个 canary：1 supported、1 refuted。
- canary 通过后以 concurrency=2 跑 52 条首轮；不因并发共享 Agent、Interaction、workspace 或 archive。
- 失败或语义不合格的 case 最多再独立采样两次；每次使用新 episode ID，最多三次总尝试。
- 同一 case 若多条通过，只保留质量最高的一条进入 accepted release，其余保留但不训练。

### 5.2 三层筛选

第一层是不可放宽的工程门禁：

- 正常到达二元裁决，无 engineering error。
- strict scheduler/protocol/route audit 通过。
- 没有 fatal boundary action、未纠正协议拒绝、伪工具结果或缺失 canonical trace。
- Evidence 可回溯到成功工具调用、真实页面和逐字 quote。

第二层在 rollout 完成后加载 private gold，执行结构化事实门禁：

- runtime `real` 对应 supported，`fake` 对应 refuted，必须一致。
- 中心 ImageClaim/observed fact 对准 `decisive_fact` 和 `claim_atom` 的 subject-event-slot。
- refuted 必须命中 `key_error.slot`，并区分 depicted value 与 verified value；supported 不得制造错误点。
- 至少一条裁决 Evidence 满足 `evidence_target.binding`、`required_directness=direct` 和正确 stance。
- Evidence URL 可以不同，但必须是同一完整关系，quote 必须确实来自实际访问页面。
- 最终 basis 不得越过 `boundary.does_not_prove`。

这层只比较结构化关系和值，不用宽泛字符串包含规则替代语义资格。

第三层复用冻结的 gold-free Gemini 轨迹综合审计，只检查图像理解、调查进展、搜索方向、Evidence 使用和 belief revision：

- 每条通过前两层且未命中缓存的轨迹最多一次调用。
- 审计看不到 private gold，也不能覆盖前两层硬门禁。
- 保存模型、Prompt、调用 ID、token 数、请求/响应 hash 和各维分数。
- canary 后冻结质量阈值，正式批次中不得按 case 改阈值。

### 5.3 接受门槛

- 不要求 52/52 全部生成成功；失败轨迹不能硬修成训练答案。
- 30-case pilot 至少接受 30 个三门禁全通过的 case，且 revision 后 validation 的
  8 个 case 均有合格目标；该数量调整不得放宽任何逐轨迹事实或过程门禁。
- 若低于门槛，先按失败分布诊断通用 runtime/检索/评分问题；不得降低筛选标准。
- 生成 HTML/JSON 审核队列，人工只处理结构化门禁无法判定的少数边界项。

## 6. SFT 样本契约

一条训练样本对应一个阶段决策，不是完整长对话：

```text
immutable brief
+ protected workspace
+ selected archive spans
+ current image/crop（阶段需要时）
+ available tools
-> one canonical assistant action
```

导出阶段：

- perception
- planning
- react
- decision
- reflection
- judgment

监督规则：

- 只监督模型可见的 canonical assistant 输出和原生 tool call。
- system/user/context/tool result 的 loss mask 为 0。
- 不监督 hidden thinking，不把旧 reasoning 传给后续阶段。
- Judgment 必须携带真实 basis；不能从 gold 合成一个 runtime 从未产生的答案。
- 图片只在阶段确实需要时进入样本，保持受控分辨率与 `IMAGE_MAX_TOKEN_NUM`。
- 每条样本记录 source case、episode、step、stage、trace hash、image hash 和 split。
- 任何 private gold 字段、snapshot 路径、认证 Evidence ID 或 legacy-20 身份命中即整批拒绝。

## 7. 导出与离线门禁

正式导出前需要补一条明确的新契约路径：`ifv-existing-eval-package-v1` / `ifv-scoring-gold-v1` 不能伪装成旧 v0.3 release。教师 runner 和离线 scorer 显式读取新 manifest；Agent 侧仍只接收 public runtime rows。

导出顺序：

1. accepted teacher release。
2. provider-neutral perception/policy examples。
3. frozen split 注入和 source-family 去重验证。
4. ms-swift `messages/tools/images` 转换。
5. dataset audit 与 content hash manifest。

必须验证：

- 旧 20 case ID 和图片哈希全量拒绝。
- 训练/验证 case、图片、source family 无交叉。
- 六个 stage 文件均非空；缺 stage 只能由 manifest 明确说明，不能悄悄补空样本。
- tool schema 与推理期注册表一致。
- 每条 assistant target 至少有一个非 padding、非 image、非 context 的 loss token。
- 没有目标被静默截断。

## 8. Token 与 thinking 策略

- SFT 继续使用 `enable_thinking=false`，学习可见阶段输出，不学习长 hidden reasoning。
- 这不妨碍推理期按阶段动态启用 Qwen thinking；推理 reasoning 仍独立归档且不继承。
- 先对全部 accepted rows 使用 Qwen3.5 正式 processor 统计 token，再冻结 `max_length`。
- 从 4096、8192、16384、32768 中选择能覆盖全部 loss-bearing target 的最小档位。
- 若输入过长，优先压缩重复网页、旧措施和已被 workspace 取代的历史；不能截掉决定性 Evidence、当前冲突、可用工具或 target。
- Agent 运行时单请求仍允许到 128K；SFT 阶段样本不等同于完整运行时上下文。

2. 确认物理 GPU 4、5、6、7 显存均低于 1 GiB，无残留 worker。
3. 使用 SFT conda 环境，验证 CUDA 12.8、DeepSpeed、ms-swift 和模型 hash。

5. 执行真实四 rank NCCL all-reduce。

训练 smoke 顺序：

- 1-step：完整 forward/backward，LLM、vision、aligner 均有有限梯度。
- 3-step：保存、恢复并继续到第 3 step。
- 独立进程重载 checkpoint，跑 image/template/tool schema probe。
- 20-step：验证显存、吞吐、日志、评估和 checkpoint 生命周期，不用于判断模型效果。

任何 CUDA/NCCL/OOM/NaN、目标截断、loss mask 为空或恢复不一致都会停止正式训练。

## 13. 时间预估与实测外推

时间必须拆开记录，不能把教师检索、数据处理、GPU 训练和最终评测混为一个数字。

当前准备阶段的保守区间：

| 阶段 | 初步区间 | 主要变量 |
|---|---:|---|
| 52 条 Gemini 首轮教师轨迹 | 1.5–4 小时 | 单 case 搜索动作、网页延迟、concurrency=2 |
| 失败项最多两轮重采样与筛选 | 0.5–3 小时 | 首轮通过率 |
| stage 导出、模板与 token 审计 | 15–45 分钟 | accepted row 数、图片处理 |
| 1/3/20-step 与重载 smoke | 45–90 分钟 | 模型加载、checkpoint I/O、ZeRO 初始化 |
| 四卡正式 SFT（3 epoch） | 2–8 小时 | stage row 数、max length、ZeRO-3 offload 吞吐 |
| checkpoint serving 与 legacy-20 | 0.5–2 小时 | 每 case action 数与评测并发 |

上述只是排程区间，不作为完成报告。正式训练前写出 `time-estimate.json`，至少包含：

```text
accepted train/validation cases
train/validation stage rows
token p50/p90/p95/p99/max
selected max_length
global batch
epochs
20-step warmup-excluded seconds/step
checkpoint/eval overhead
predicted optimizer steps
predicted wall-clock range
```

正式 SFT 的中心估计使用：

```text
optimizer_steps = ceil(train_rows * epochs / global_batch)
train_seconds = optimizer_steps * measured_seconds_per_step
wall_clock = train_seconds + validation + checkpoint + startup overhead
```

20-step 的前 5 step 作为初始化/缓存预热，不进入稳态 `seconds/step`；用后 15 step 的中位数和 p90 分别给出中心值与保守上界。训练期间每 step、每次 validation、save 和 resume 都记录开始/结束时间，完成后比较预测与实际误差。

若 token 审计选择 16K 或 32K 档，必须重新运行对应长度的 20-step smoke，不能沿用 2K smoke 外推。

## 15. 四卡显存策略实测与最终选择

GPU 4–7 上使用同一真实 32K 数据与完整参数训练实测三种 ZeRO-3 策略：

| 策略 | train step | validation | 结果 |
|---|---:|---:|---|
| parameter + optimizer 双 CPU offload | 192.4 秒 | 149.1 秒 | 通过，但吞吐过低 |
| parameter/optimizer 均驻 GPU | 55.72 秒 | 未完成 | validation 长样本 OOM |
| parameter 驻 GPU，仅 optimizer CPU offload | 60.19 秒 | 27.04 秒 | 通过，无 OOM/NCCL/NaN |

最终冻结 `training/configs/deepspeed/zero3-optimizer-offload.json`。3-step、20-step 与 pilot30 profile 均使用该配置，不再把双卸载作为正式路径，也不因纯 GPU 单步更快而接受 validation OOM。

## 16. 吞吐优化后的正式配置

20-step batch=1 全量 smoke 的训练本体为 20 step / 666 秒（约 33.3 秒/step，每 step 4 条样本）。该配置的常见样本显存只有约 16.3 GiB，未能有效使用 A100 40GB。

在不改变模型、数据、32K 上限、ZeRO-3、完整参数训练或学习率的前提下，新增两道真实数据门禁：

1. 每卡 batch=2、两条 19.8K/20.6K token 的真实 react 样本同时训练，峰值约 30.9 GiB，完整保存、评估通过；
2. 全量数据 batch=2 + ms-swift 原生 `group_by_length` 跑 10 step，显存约 35.0 GiB、无 OOM/NCCL/NaN，训练本体 420 秒处理 80 条样本。

因此正式 pilot 改为每卡 batch=2、global batch=8、99 optimizer steps；`ceil(262 train stage rows × 3 epochs / 8)=99`，仍对应三遍冻结训练数据。学习率保持 `1e-5`，不采用线性缩放或新的优化算法。batch=3 未进入正式候选：batch=2 在最坏长样本下仅保留有限显存余量，继续扩大风险不成比例。
