Qwen3.5 服务与八轮协议门禁已经通过。正式 Queen 的 Planning 输入经账本确认只有约

字段，直到耗尽整个 `max_tokens`。

依据 Qwen3.5 官方模型卡和 vLLM reasoning 文档，冻结以下第一轮修复：

- Qwen3.5 Thinking 使用官方通用采样参数：`temperature=1.0`、`top_p=0.95`、
  `top_k=20`、`min_p=0`、`presence_penalty=1.5`、`repetition_penalty=1.0`；
- 非 Thinking 使用官方通用 instruct 参数：`temperature=0.7`、`top_p=0.8`，其余保持；
- `thinking_token_budget` 与 `max_tokens` 分离：Planning 1,024，Discrepancy Decision
  和 Judgment 2,048，Reflection 1,536；
- Qwen3.5 Planning 的 `max_tokens` 恢复为 8,192；预算后的结构化正文仍有充足空间；
- Prompt 只补充一行字段签名，使模型看见 `ImageAccountPlanningOutput` 的字段，不复制完整
  JSON Schema，不增加样例规则；
- reasoning 作为独立 content-addressed 诊断 artifact 保存，明确标记不进入后续上下文、
  Evidence 或 canonical action；
- 正式 serving 不启用 MTP speculative decoding。vLLM 当前仍有 Thinking budget 与
  structured output 在 MTP 下错过 `</think>` 边界的公开缺陷。

相同 Queen 输入隔离结果：无 Thinking 为 8 秒但退化为图像表层复述；原 Prompt + 1,024
Thinking 为 20.6 秒并首次产生“实际使用什么交通工具”的开放查询，但最终 Claim 仍偏表层；
简短字段签名 + 1,024 Thinking 为 17.4 秒，输出直接现实命题，并提出核查传统礼仪马车与
双层巴士的关系。下一门禁是本地全量测试、服务器同步、Queen 完整真实轨迹和 strict audit；
Queen 零工程错误后才运行正式 20 例。

## 2026-07-22 执行更新：Queen 第一轮完整运行

提交 `5d7b800` 的真实 Queen 运行在约 205 秒后以 engineering error 结束。Planning

finding。修复与 Gemini Interactions 的成熟语义对齐：协议纠正有独立有限预算，不消耗
ReAct action round，不放宽 schema。Planning 同时只用一句通用定义强调 Claim 是图像的
中心现实断言，且 high salience 必须足以改变整图 verdict；不加入 Queen、bus、coach、年份、
URL 或固定查询规则。本地门禁为 `456 passed`，下一步只重跑 Queen。

第二轮 Queen 在 147 秒内执行 7 个真实工具动作后再次暴露工程错误。协议纠正已不再占用
action round；新错误是 `compare_with_reference` schema 把三个待选参考图放进 enum，却因
该字段在另一种视觉复检模式下由 runtime 注入而将 `reference_url` 从 required 中删除。
Qwen 因而合法地产生缺少 URL 的调用，校验器连续拒绝。修复要求所有带有 runtime route
constraint 的选择字段进入 required；只有没有 constraint、确由 pending visual question
注入的字段才从模型 schema 隐藏。Planning 同时进一步压缩为“一个保留中心人物—事件—关系
的高显著 Claim，额外 Claim 只用于独立的 verdict-changing assertion”。

第三轮 Queen 已验证以上两项工程修复：Planning 保留了中心人物—事件—交通工具关系，
协议纠正和参考图 selector 均不再中断。运行在 24-action 上限后进入 bounded Judgment，
但搜索大多核查图片中的具体值、相同图片和错误 OCR，没有优先建立同一现实关系的实际值；
网页正文虽包含对应的实际关系，窄 `retrieval_goal` 又使抽取器未选为 Evidence。最终编译
basis 为空，Judgment 擅自增加 Discovery/视觉 ID，被严格 validator 作为 engineering error
拒绝。下一轮只做三处通用的小改动：Planning 的 SearchHypothesis 明确询问实际发生了什么，
ReAct 以现实事实而非图片所提具体值或相同图片为检索中心，网页抽取允许选取未复述争议值、
但给出同一争议关系实际值的正文。三处均不改变 stance 规则，不加入样例关键词、URL 或固定
查询。门禁通过后只重跑 Queen；先观察有 Evidence 的 Judgment，再决定是否调整机械 basis
复制协议。

第四轮验证了开放事实提示的方向有效：Planning reasoning 和第二条 Hypothesis 都提出核查
现实交通方式。但最终结构化输出把中心关系拆成两个高显著表层 Claim，第一条来源/同图路线
又因优先级独占调度；该 Task 已执行 17 个动作后仍可无限选择 archive recall，连续四次重复
同一 recall 导致协议纠正预算耗尽，第二条现实事实路线从未获得调度。下一轮修复保持在输出
与控制面：Planning schema 要求且仅允许一个完整中心关系 high Claim，附加 Claim 只能为
medium；archive recall 只有 Task 已产生档案材料时才开放，每个 Task 最多两个 recall/read
周期，`read_evidence` 只在存在 pending ID 时暴露。真实检索路线和 24-action 上限不变，不用
增加纠正次数掩盖路线未切换。

## 1. 已确认决策

- 正式学生基座：`Qwen/Qwen3.5-9B` 后训练模型。
- 同一权重同时承担图像理解、工具调用和裁决，不拆成两套 Agent。
- 高频 Verification 工具路由默认关闭 Thinking；Planning、Evidence Decision、Reflection、Judgment 默认开启 Thinking。
- 单请求服务上下文为 128K 以上；不把 32K 当作上下文管理。
- 历史消息只保留可见最终输出，不重复注入旧 reasoning。
- 20 例只用于开发评估，禁止进入 SFT、RL、教师数据或合成数据。
- Prompt 保持简短，只描述任务、工具和输出契约；不得为单例堆规则。
- gpu-13 只使用物理 GPU 4、5、6、7，最多四张；运行服务先用 4、5。

## 2. 当前切换依据

Qwen3-VL-8B-Thinking 的服务与协议门禁已经通过，但真实 Queen 暴露出两个结构性问题：

- Planning 单次生成 7,255 token；每个 ReAct 回合都会重新长思考，串行延迟高。
- 一个 Verification 请求在生成接近 8,192 token 后由服务返回 400；同一输入重放仅生成 1,563 token、22 秒完成并正确调用工具。

Qwen3.5-9B 官方支持在同一权重上用 `chat_template_kwargs.enable_thinking` 动态切换，并明确要求多轮历史不保留旧思考内容。这与当前短生命周期、显式 workspace/archive 传递的 Agent 架构一致。

## 3. 执行顺序

### Phase A：独立 Serving

1. 在 `/gsdata` 创建全新 Python 3.11 环境，不修改任何旧 Qwen、Gemini、SFT 或 RL 环境。
2. 使用官方要求的 vLLM main/nightly，固定完整依赖清单和 SHA-256。
3. 下载并校验 `Qwen3.5-9B` 四个权重分片、模型 revision、processor 和 chat template。
4. 在物理 GPU 4、5 上启动 TP=2、BF16、loopback 服务；上下文至少 131072。
5. 使用官方 `qwen3` reasoning parser 与 `qwen3_coder` tool parser。

门禁：

- health 和模型列表；
- 128K 上下文声明；
- 单图理解和 OCR 敏感输出；
- Thinking 开、关均可观察且不会污染 canonical action；
- JSON Schema；
- 正好一次 native tool call；
- `role=tool` continuation；
- 八轮独立短链；
- 错误正文、超时、取消和干净停止可观测。

### Phase B：Queen 工程门禁

只运行 Queen，并通过逐步落盘的 `events.jsonl` 监控每个请求：

- stage；
- 输入、输出 token；
- Thinking 开关；
- 工具动作和结果；
- HTTP 错误正文；
- 最终 verdict 或 engineering error。

此阶段只修通用工程问题：协议、schema、parser、超时、上下文、持久化和工具边界。不得修 Queen 专用语义。

通过条件：完整运行到二元裁决，零 engineering error，严格轨迹审计通过。

### Phase C：冻结并运行 20 例

Queen 通过后冻结以下配置：

- 模型 revision；
- vLLM lock；
- GPU/TP/context；
- 各阶段 Thinking；
- 输出 token 上限；
- Prompt revision；
- 工具和网页抽取配置。

先以 concurrency=1 启动并监控；确认 KV cache 和系统内存安全后才提高并发。20 例期间不调 Prompt 或单例策略。

若出现 engineering error，只修通用问题并重跑受影响批次，直到 20/20 工程层通过。

### Phase D：轨迹综合分析与小幅调整

只在 20/20 工程通过后执行。按总体分布分析：

- 图像理解是否随新证据更新；
- 是否从伪造的具体值发散到真实关系槽位；
- Discovery 是否被正确提升为 Evidence；
- 路线重复、耗尽和正常二元退出；
- 每阶段 token、耗时和无效长思考；
- `real|fake` 错误类型及证据链质量。

调整必须简短、通用、一次一个变量；调整后重跑同一冻结 20 例比较，不得引入样例补丁。

## 4. 训练数据契约

一条训练样本对应一次阶段决策，不是整个长对话：

```text
immutable brief
+ protected workspace
+ selected archive spans
+ current image/crop（该阶段确实需要时）
+ available tools
-> one canonical stage action
```

保留：决定性 Evidence、未解决冲突、当前路线、图像理解修订、精确 archive 引用。  
压缩：重复网页、旧模型措辞、无效工具输出、已被新 workspace 取代的历史。  
reasoning 可作为过程评分对象，但不反复拼回后续请求，也不直接作为最终监督目标。

20 例的 case ID、图像哈希和所有派生轨迹进入训练拒绝清单。

## 5. SFT 基建

只采用已有成熟框架，首选经过 Qwen3.5 多模态实测的 ms-swift + DeepSpeed/FSDP；若真实 ABI 或显存门禁失败，记录最小复现后切换官方 Transformers + DeepSpeed/FSDP，不自写训练循环。

顺序：

1. processor/chat-template/token-mask 离线审计；
2. 非 20 例数据的 1-step forward/backward；
3. 梯度覆盖 LLM、视觉编码器和 aligner；
4. 1-step 保存；
5. 恢复到 3-step；
6. 独立进程重新加载并跑图像、JSON、tool smoke；
7. 再建立正式 SFT 数据 release 和 held-out 门禁。

优先验证全参数 BF16 + ZeRO-3/FSDP；LoRA 可用于快速设施诊断，但不能冒充全参数门禁。

## 6. Agent RL 基建

采用成熟 Agent RL 框架，候选为 veRL/rLLM 等支持 Qwen3.5、vLLM rollout、断点恢复和 logprob 对齐的组合。框架选择由 gpu-13 最小真实门禁决定。

- Qwen checkpoint 随训练更新并重新采样 on-policy 轨迹。
- Gemini 只作为冻结的离线教师、过程评分器和回归基线，不生成 Qwen 的 on-policy rollout。
- v4 runtime 继续拥有工具、workspace、Evidence、停止和审计语义；训练框架不得复制第二套 Agent 状态机。
- 四卡优先采用成熟的 colocated 或 2-card rollout + 2-card training 配置，以显存和吞吐实测冻结。
- 奖励先离线 replay 和人工审计，再允许在线 RL；private gold 永不进入模型上下文。
