# Matched-pool 64K versus 120K packing benchmark — 2026-09-11

Result: prefer **65,536-token packing with SP4** as the next production candidate.
This supersedes the earlier seven-episode 120K preference, not the 131,072 context
ceiling. No production training was launched and no production defaults were changed.

## Method

`prepare_packing_comparison.py` selects 64 evenly spaced length quantiles including
both endpoints, plus four image-heavy extremes, from the fully verified policy
train split. The union is 68 complete episodes, 1,705,876 input tokens, lengths
7,328–56,100, and at most 18 image references per episode. Source hash verification
binds selection to the processor audit. No images are copied and no trajectory is
truncated or split. Comparison JSONL SHA-256:
`d8b0cdb9f7a28a4f9aae7c5827ad482b3c943674f5f0808ce7932e0b7527b194`.

Each configuration loads the same base Qwen3.5-9B model and same episode pool,
uses all four H20 GPUs, FSDP2 full shard with activation checkpointing, full-parameter
training, FlashAttention, padding-free, batch 1 per device, accumulation 1, seed 42,
and 12 optimizer steps. Save and evaluation are disabled. The 128K sample cap and
image-processing settings remain unchanged. Swift CLI `delete` maps internally
to template `raise`; strict preprocessing is enabled. An initial CLI invocation
using literal `raise` failed argument parsing before training; it is retained and
excluded from throughput comparisons.

Native packing produces 27 packs at 64K (54,532–65,377 tokens) versus 15 packs at
120K (90,443–119,705 tokens). Both pool token totals agree with the audit.

## Results

Effective input tokens are trainer token increments divided by SP degree, not raw
replicated token counters. Window time is derived from cumulative trainer timing.

| Configuration | Tokens/s, steps 7–12 | Tokens/s, steps 10–12 | Seconds/step, steps 7–12 | Max sampled GPU MiB | Projected epoch minutes, steps 7–12 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64K, SP4 | 6,423 | 6,540 | 10.00 | 79,980 | 163 |
| 120K, SP4 | 3,160 | 3,832 | 34.33 | 97,348 | 331 |
| 64K, SP2 | 4,006 | 4,014 | 31.49 | 97,328 | 261 |

All three completed with exit code zero, finite losses/gradient norms, and no OOM.
Device capacity is 97,871 MiB: both 120K/SP4 and 64K/SP2 leave roughly 0.5 GiB
at their sampled peak, versus roughly 17.5 GiB for 64K/SP4. GPU usage returned
to 1 MiB per device after the runs. No checkpoint was saved.

In this short test, 64K/SP4 delivers about 2.03 times the last-six-step throughput
of 120K/SP4, and 1.60 times that of 64K/SP2. High memory occupancy alone is not
evidence of high throughput. Logs do not establish the cause of slower larger-pack
runs; compilation, varying multimodal shapes, and memory pressure require separate
profiling before attribution.

## Interpretation limits and next candidate

These are short matched-pool tests, **not identical-token-workload epoch timings**.
Twelve steps cover different subsets under different packings; the measured windows
do not contain identical episodes. SP2 also changes effective optimization batch.
The pool is length-stratified and enriched for image-heavy extremes, not a random
full-dataset sample. Shape warmup and cache-order effects may remain, especially
for 120K. Neither loss differences nor these timing windows establish model quality
or a universal twofold speedup.

Epoch estimates divide the full training set's 62,673,659 tokens by measured
throughput, excluding startup, evaluation and saving. For 64K/SP4 the two windows
project approximately 160–163 minutes of training computation, not a completion
time guarantee. Full-data validation and a longer warm measurement remain useful
before locking a production schedule; validation-set size is still only one case.

Next candidate: `H20_PACKING=true H20_PACKING_LENGTH=65536 H20_SP=4`, batch 1,
full shard, with the 131,072 sample cap retained. Existing complete episodes all
fit 64K. Future longer episodes need a validated separate route, not silent drops.
