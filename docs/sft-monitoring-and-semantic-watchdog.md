# SFT Monitoring and Semantic Watchdog

This document defines machine-oriented monitoring for IFV SFT runs. It is
intended for an operator Agent that reads structured state and reports the
training condition; it does not require a human dashboard.

## Monitoring layers

The monitor reuses outputs already produced by ms-swift and Transformers:

- `logging.jsonl` for step, loss, evaluation loss, gradient norm, learning
  rate, token accuracy, elapsed time, ETA, memory, and step speed;
- `train.log` for framework errors and the completed-run marker;
- `resource-samples.jsonl` for process liveness, CPU RSS, GPU utilization,
  and GPU memory;
- `checkpoint-*/trainer_state.json` and checkpoint files for recoverability;
- optional behavior metrics generated by real Agent checkpoint probes.

The watchdog does not implement a second trainer and does not replace
ms-swift evaluation, checkpointing, or resume behavior.

## One-shot status

```bash
ENV=/gsdata/home/wza/conda/envs/ifv-qwen35-sft-ms-swift442
TRAINING_ROOT=/gsdata/home/wza/image-factual-verifier-v2-data/training
EXPERIMENT_ID=<experiment-id>

"$ENV/bin/python" -m ifv_training monitor-sft \
  --train-log "$TRAINING_ROOT/logs/$EXPERIMENT_ID/train.log" \
  --resource-samples "$TRAINING_ROOT/logs/$EXPERIMENT_ID/resource-samples.jsonl" \
  --checkpoint-root "$TRAINING_ROOT/checkpoints/$EXPERIMENT_ID" \
  --output "$TRAINING_ROOT/logs/$EXPERIMENT_ID/monitor-latest.json"
```

The command emits JSON with:

- lifecycle: `waiting`, `running`, `inactive`, `completed`, or `failed`;
- health: `healthy`, `warning`, or `critical`;
- current and maximum step, percentage, ETA, and last-update age;
- current loss, eval loss, gradient norm, learning rate, token accuracy,
  memory, and step speed;
- latest GPU/process sample and latest checkpoint;
- structured alerts and a recommended next action.

## Continuous Agent polling

```bash
"$ENV/bin/python" training/scripts/train/watch_sft.py \
  --train-log "$TRAINING_ROOT/logs/$EXPERIMENT_ID/train.log" \
  --resource-samples "$TRAINING_ROOT/logs/$EXPERIMENT_ID/resource-samples.jsonl" \
  --checkpoint-root "$TRAINING_ROOT/checkpoints/$EXPERIMENT_ID" \
  --output "$TRAINING_ROOT/logs/$EXPERIMENT_ID/monitor-latest.json" \
  --interval-seconds 60 \
  --stale-seconds 900 \
  --stop-on-terminal
```

The status file is replaced atomically so another Agent can read it while the
watcher is updating.

## Semantic behavior input

Training loss cannot prove that the fact-checking Agent improved. Real Agent
checkpoint probes may append one aggregate row per evaluated checkpoint:

```json
{"global_step": 0, "metrics": {"verdict_accuracy": 0.80, "strict_evidence_sufficiency_rate": 0.50, "trace_audit_pass_rate": 0.70, "format_valid_rate": 1.0, "think_present_rate": 1.0, "engineering_failure_rate": 0.0, "majority_verdict_rate": 0.60}}
{"global_step": 250, "metrics": {"verdict_accuracy": 0.83, "strict_evidence_sufficiency_rate": 0.57, "trace_audit_pass_rate": 0.80, "format_valid_rate": 1.0, "think_present_rate": 1.0, "engineering_failure_rate": 0.0, "majority_verdict_rate": 0.57}}
```

Pass the file through `--behavior-metrics`. The monitor detects:

- verdict-accuracy regression from the best prior probe;
- strict-evidence-sufficiency regression;
- missing or malformed output structure;
- loss of visible reasoning;
- engineering-failure growth;
- collapse toward one verdict.

The fixed probe set may overlap the final test set, but its case IDs and
artifacts must never be added to the SFT training datasets.

## Framework features and cautions

Use ms-swift and Transformers features where they are reliable:

- keep `logging_steps`, `eval_steps`, and `save_steps` explicit;
- keep evaluation and checkpoint steps aligned when selecting by eval loss;
- use `logging.jsonl` rather than scraping terminal progress bars;
- retain optimizer, scheduler, and RNG state for resumable checkpoints;
- use `validate-checkpoints --behavior-metrics` for final checkpoint ranking.

Do not enable framework early stopping as the only quality gate. The built-in
callback stops on the configured evaluation metric, normally loss; it cannot
detect a model that has lower teacher-forced loss but worse investigation
behavior. Semantic alerts are therefore advisory and require checkpoint
inspection rather than automatic termination from a small probe.

Do not enable `load_best_model_at_end` without verifying that evaluation and
save strategies match and that `save_steps` is a multiple of `eval_steps`.
Reloading a full ZeRO-3 checkpoint also adds substantial storage I/O.

The ms-swift `perf_log` callback can add MFU metrics, but it estimates device
TFLOPS at startup. Enable it only after a controlled smoke test on the target
GPU model; the existing resource sampler is the default production signal.

## Interpretation

The watchdog classifies mechanical failures such as process loss, stale
progress, OOM, NCCL errors, NaN/Inf, missing required validation, and malformed
semantic output as critical. Loss, gradient, eval-loss, and semantic-score
regressions are warnings unless they coincide with a hard failure.

The operator Agent should report:

```text
RUNNING step=428/1000 loss=0.63 eval_loss=0.71 grad_norm=2.8
ETA=7h18m checkpoint=400 alerts=0
```

Checkpoint selection remains behavior-first:

1. valid reasoning and tool-call contract;
2. strict evidence sufficiency and trace-audit pass rate;
3. verdict accuracy;
4. engineering reliability;
5. eval loss as a secondary signal.
